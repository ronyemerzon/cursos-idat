Guía Maestra del Proyecto EduPortal: De Principio a Fin

Aprende, domina y explica cada componente del proyecto como si lo hubieras desarrollado desde cero
Equipo: Rony Pascual, Alison Laulate, Cristhian Moreno Curso: Interfaces 3 (IDAT) Rúbrica: 20/20

1. Visión General: ¿Qué construimos y por qué?

El proyecto resuelve la necesidad de una institución educativa de digitalizar la gestión de cursos y usuarios mediante una Single Page Application (SPA).

El sistema se compone de dos proyectos totalmente desacoplados:

  1. Backend (eduportal-backend): Una API REST desarrollada en Java con Spring Boot 3, asegurada con Spring Security 6 y JSON Web Tokens (JWT), conectada a una base de datos Microsoft SQL Server llamada EduPortalDB.
  2. Frontend (eduportal-frontend): Una SPA en Angular 18+ con componentes Standalone, enrutamiento con Lazy Loading, protección con Guards (AuthGuard, RoleGuard, LoginGuard), e interceptores HTTP para inyectar tokens Bearer automáticamente.

2. La Base de Datos: Microsoft SQL Server

En lugar de usar bases de datos temporales, se utilizó SQL Server para asegurar persistencia real. Las tablas diseñadas son:

  • dbo.users: Almacena los usuarios, roles (ROLE_ADMIN, ROLE_PROFESOR, ROLE_ESTUDIANTE), estado y la contraseña (encriptada con BCrypt).
  • dbo.courses: Almacena el catálogo de asignaturas con código, créditos, categoría, docente asignado, capacidad máxima de alumnos y contador de matriculados.
💡 ¿Cómo responder si el profesor pregunta sobre las contraseñas?

"Profesor, las contraseñas nunca se guardan en texto plano en la base de datos. Usamos el algoritmo BCrypt con 10 rondas de hashing a través de PasswordEncoder en Spring Security. Incluso si alguien tiene acceso directo a la base de datos SQL Server, no podrá descifrar la clave original."

3. El Backend Spring Boot: Estructura y Seguridad

El backend sigue una arquitectura clásica por capas:

  • model/: Clases JPA anotadas (@Entity, @Table) que mapean directamente las tablas de SQL Server.
  • repository/: Interfaces que extienden JpaRepository para realizar operaciones de base de datos sin escribir SQL manual.
  • service/: Lógica de negocio (login, encriptación, validación de cupos de matrícula y reglas de negocio).
  • controller/: Endpoints REST (@RestController) que exponen los servicios vía HTTP en formato JSON.
  • config/: Configuración de seguridad (SecurityConfig), CORS y el filtro JwtAuthenticationFilter.

¿Cómo funciona la autenticación JWT en el Backend?

  1. El cliente hace una petición POST /api/auth/login enviando { email, password }.
  2. El servicio AuthService busca el usuario en SQL Server y valida el password con passwordEncoder.matches(...).
  3. Si es correcto, la clase JwtTokenProvider genera una cadena JWT firmada con la clave secreta institucional y algoritmo HMAC-SHA256.
  4. El token incluye en su payload (Claims): id, email, name y role, con una vigencia de 24 horas.

4. El Frontend Angular: Enrutamiento, Guards y Componentes

4.1. Enrutamiento y Lazy Loading (app.routes.ts)

Para que la aplicación cargue rápido, cada página se configuró con Lazy Loading mediante loadComponent: () => import(...). El enrutamiento es jerárquico: 

export const routes: Routes = [
  { path: 'login', canActivate: [loginGuard], loadComponent: ... },
  {
    path: '',
    component: MainLayoutComponent,
    canActivate: [authGuard], // Protege todo el layout
    children: [
      { path: 'dashboard', loadComponent: ... },
      { path: 'usuarios', canActivate: [roleGuard], data: { roles: ['ADMIN'] }, loadComponent: ... },
      { path: 'cursos', loadComponent: ... },
      { path: 'cursos/:id', loadComponent: ... }, // Ruta parametrizada
      { path: 'perfil', loadComponent: ... }
    ]
  },
  { path: 'unauthorized', loadComponent: ... }, // Vista 403
  { path: '**', loadComponent: ... }            // Vista 404
];

4.2. Los 3 Guards Explicados

  • auth.guard.ts: Revisa si hay un token JWT en localStorage y verifica que su fecha de expiración (exp) sea mayor al tiempo actual. Si no, redirige a /login.
  • role.guard.ts: Obtiene el rol del usuario desde el JWT y lo compara con el arreglo data['roles'] de la ruta. Si un estudiante entra a /usuarios, lo manda a /unauthorized.
  • login.guard.ts: Si el usuario ya está autenticado, no lo deja volver al formulario de login y lo lleva directo al /dashboard.

4.3. Los Interceptors en Cadena (app.config.ts)

Angular 18 usa interceptores funcionales con HttpInterceptorFn:

  • jwtInterceptor: Clona cada petición saliente de HttpClient y le añade el header Authorization: Bearer <token>. Así el backend sabe quién hace la petición.
  • errorInterceptor: Si el backend responde un error 401 (token expirado), desloguea y manda a login. Si responde 403 (prohibido), manda a /unauthorized.

4.4. Pipes y Directivas Personalizadas de Propia Creación

  • RoleNamePipe (| roleName): Convierte ROLE_ADMIN a "Administrador", ROLE_PROFESOR a "Docente" y ROLE_ESTUDIANTE a "Estudiante".
  • StatusBadgePipe (| statusBadge): Devuelve la clase de color y la etiqueta adecuada según el estado del curso o usuario.
  • TruncateTextPipe (| truncateText:80): Recorta las descripciones de los cursos para que todas las tarjetas se vean alineadas y elegantes.
  • HasRoleDirective (*appHasRole="['ADMIN']"): Directiva estructural que oculta botones de administración en la vista si el usuario no tiene el rol necesario.
  • HoverCardDirective (appHoverCard): Directiva de atributo que da efecto de elevación y sombra dinámica a las tarjetas al pasar el cursor.

5. Banco de Preguntas Típicas del Docente (Sustentación)

Revisa estas preguntas y respuestas para asegurar la máxima nota en tu exposición:

❓ 1. ¿Cómo viaja el Token JWT desde que el usuario inicia sesión hasta que consulta los cursos?
Respuesta: Al hacer login, el backend valida las credenciales y devuelve el token en formato string. El AuthService de Angular guarda ese token en el localStorage. Luego, cuando cualquier servicio hace peticiones con HttpClient, nuestro jwtInterceptor intercepta la petición saliente, recupera el token del localStorage y le añade la cabecera HTTP Authorization: Bearer <token> de manera automática y transparente.
❓ 2. ¿Qué diferencia hay entre AuthGuard y RoleGuard?
Respuesta: AuthGuard verifica autenticación (es decir, si el usuario está logueado y su token JWT es válido). En cambio, RoleGuard verifica autorización (es decir, qué rol tiene ese usuario y si ese rol específico tiene permiso para acceder a la ruta solicitada, por ejemplo solo administradores para la ruta /usuarios).
❓ 3. ¿Por qué usamos Lazy Loading en las rutas?
Respuesta: Porque en aplicaciones grandes, cargar todos los componentes en el paquete inicial (bundle) hace que la aplicación tarde en abrir. Con Lazy Loading (loadComponent: () => import(...)), Angular solo descarga los archivos JavaScript del módulo que el usuario está visitando en ese momento, logrando una carga instantánea.
❓ 4. ¿Cómo implementaron una Directiva personalizada de propia creación?
Respuesta: Creamos HasRoleDirective (*appHasRole) como directiva estructural. Inyecta TemplateRef y ViewContainerRef. Se suscribe al currentUser$ del AuthService y, si el usuario logueado no tiene el rol necesario, ejecuta this.viewContainer.clear() para eliminar ese elemento del DOM, impidiendo que el usuario vea opciones no autorizadas.
❓ 5. ¿Qué sucede si el token JWT expira mientras el usuario está usando la aplicación?
Respuesta: Cuando el token expira, el backend Spring Boot rechaza la petición devolviendo un código de estado 401 Unauthorized. Nuestro errorInterceptor en Angular captura ese error 401 globalmente, ejecuta el método authService.logout() para limpiar el localStorage y redirige automáticamente al usuario a la pantalla de /login mostrando una notificación toast explicándole que su sesión ha caducado.
